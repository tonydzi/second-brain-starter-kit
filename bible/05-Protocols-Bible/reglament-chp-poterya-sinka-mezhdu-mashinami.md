# ЧП: потеря синка между машинами — аудит, корень, профилактика, план действий

> Заказ Антона (2026-06-26): «полный аудит инцидента 24–26 июня (потеря связи/синка между компами): понять ПРИЧИНУ, как не допустить её в будущем (копаем в КОРЕНЬ fix-root-cause-not-symptoms [internal]), и сделать ПЛАН ДЕЙСТВИЙ на случай ЧП, когда машины не видят друг друга через синк». Для всех акторов (Антон + ассистенты + AI). Связано с [[reglament-multi-machine-claude-i-peredacha-mezhdu-mashinami]] (§4 лестница каналов) и памятью syncthing-v21-gotchas [internal], machine-bus-telegram-rail [internal].

## 0. TL;DR
- **Что сломалось:** связь Syncthing между хабом и пирами (ноут, MacBook-[коллега]) умерла на ~12–18 часов.
- **КОРЕНЬ (два слоя):** (1) **сторож-watchdog убивал демон по ложному сигналу** — после апгрейда Syncthing v2.1 API-ключ переехал из `config.xml` в `config.json`/SQLite → пинг сторожа стал отдавать `403` → сторож трактовал `403` как «демон мёртв» → **пилил Syncthing каждые ~18 сек**, рвя любую сессию; (2) **дрейф Device ID без канонической записи** — после переезда хаба на Palo Alto PC его Syncthing-личность сменилась на `EEAETB6`, а пиры держали устаревший `2KPYBY4`, и **нигде не было записано, какой ID правильный** → рукопожатие рвалось («unknown device / Hello → forcibly closed»).
- **Усилители:** единственный канал Claude↔Claude (`[шина]`) сам ездит на Syncthing → умер вместе с ним → машины онемели, диагноз раздробился по сессиям (ноут сделал НЕВЕРНЫЙ вывод «верни 2KPYBY4» без hub-side фактов). Плюс на хабе не было непрерывного git-бэкапа конфига.
- **Чем лечили (26.06):** перешли на Telegram-шину, хаб опубликовал VERIFIED Device ID, пиры вписали `EEAETB6` → ноут+[коллега] онлайн. Сторож пофикшен (403=жив + TCP-fallback). Device ID записан в реестр.

## 2. КОРЕНЬ (5 почему — копаем до причины, чья ликвидация убивает класс)
**Симптом:** «3 пира → 0», сессии рвутся, синк не встаёт.

1. *Почему синк лёг?* → демон Syncthing постоянно перезапускался И пиры отвергали хаб.
2. *Почему перезапускался?* → сторож-watchdog убивал его каждые ~18 сек.
3. *Почему убивал?* → его health-пинг получал `403` и трактовал как «демон мёртв».
4. *Почему `403`?* → Syncthing v2.1 перенёс API-ключ из `config.xml` в `config.json`/SQLite, а сторож пинговал старым ключом → CSRF/403.
5. *Почему `403`→kill?* → **КОРЕНЬ A:** health-чек был написан так, что его режим отказа = «убить то, что он стережёт», по ОДНОМУ неоднозначному сигналу, без TCP-подтверждения и без circuit-breaker. **Монитор, который убивает по двусмысленности, превращает безобидную смену формата ключа в аварию.**

Параллельная ветка отказа:
1. *Почему пиры отвергали хаб?* → у хаба ID `EEAETB6`, а пиры ждали `2KPYBY4`.
2. *Почему ждали старый?* → после переезда хаба ID сменился, но **нигде не записано, какой ID канонический** → пиры не могли узнать правильный.
3. **КОРЕНЬ B:** **дрейф идентичности без источника истины.** Реестр `machines.json` не хранил Device ID хаба → дрейф нельзя было ни заметить, ни исправить уверенно (ноут даже сделал ОБРАТНЫЙ вывод «верни 2KPYBY4»).

Усилители (не первопричины, но удлинили простой):
- **КОРЕНЬ C:** единственный канал Claude↔Claude (`[шина]`) ездит на Syncthing → умер вместе с ним. Нет out-of-band канала → машины онемели, диагноз раздробился, сессии пришли к ПРОТИВОРЕЧИВЫМ выводам.
- **КОРЕНЬ D:** на хабе не было непрерывного git-бэкапа конфига (отдельная хрупкость того же класса; закрыт 2026-06-26).

## 3. Как НЕ допустить — профилактика (лечим КЛАСС, не экземпляр)
### 3A. Сторож НИКОГДА не убивает по одному двусмысленному сигналу (против КОРНЯ A)
- **Любой HTTP-ответ (вкл. 401/403) = процесс ЖИВ.** «Мёртв» = только refused/timeout на TCP-уровне. *(сделано на хабе и ноуте)*
- **N подряд провалов + экспонента бэкоффа** прежде чем хоть что-то трогать; одиночный сбой игнорируем.
- **Circuit-breaker:** если перезапусков > X за Y минут — **СТОП и пинг человеку**, а не пили дальше. Сторож-пила хуже отсутствия сторожа. *(TODO — собрать)*
- **API-ключ пинить детерминированно** (env `STGUIAPIKEY`), не зависеть от того, в каком файле его держит версия. *(сделано)*

### 3B. Канонический реестр Device ID + детект дрейфа (против КОРНЯ B)
- **Каждый Device ID записан в `machines.json`** (хаб `EEAETB6`, ноут `JR2M6T4`, [коллега] `J2RQJA4`, [коллега] `MJKUK3V`). *(сделано 2026-06-26)*
- **Сменилась личность (миграция/переустановка) → машина НЕМЕДЛЕННО публикует новый verified ID в шину + обновляет реестр;** пиры верифицируют out-of-band прежде чем доверять.
- **Детект дрейфа:** периодическая проверка `live myID == реестр`; расхождение = флаг. *(TODO — в `/sync-check` или ночной чек)*
- **Правило идентичности:** если `myID != EEAETB6` — демон на ЧУЖОМ home; чинить home, **НЕ** пере-паривать пиров на временный ID. И **НИКОГДА не откатывать на старый ID, если другой пир уже работает на новом** (сломает работающего).

## 4. ПЛАН ДЕЙСТВИЙ при ЧП «компы не видят друг друга» (RUNBOOK)
Когда синк лёг / пир молчит / `/sync-check` красный — по шагам, не угадывая:

0. **ДЕТЕКТ.** Сигнал: пропал heartbeat / пир сообщил о тишине / `/sync-check` red / `/rest/system/connections` показывает `connected:false`.
1. **СМЕНИ КАНАЛ.** Вся координация → **Telegram-шина `/bus`** немедленно (она не зависит от Syncthing). Молчание ≠ ок.
2. **УСТАНОВИ ИСТИНУ НА ХАБЕ (факты, не память, не один пир):**
   - `GET /rest/system/status` → `myID` (должен быть `EEAETB6`).
   - `GET /rest/system/connections` → кто connected/нет.
   - Подтверди, что демон серверит РЕАЛЬНЫЙ волт: `GET /rest/config/folders` (пути на `[путь владельца]`) + `GET /rest/db/status?folder=anton-knowledge` (данные есть). *(Заголовок `X-API-Key: $STGUIAPIKEY`.)*
   - Если `myID` неправильный/папки пустые → демон на чужом home: чини home (§3B), не пиров.
3. **ОПУБЛИКУЙ verified Device ID хаба в шину** (out-of-band пруф): `🤖 [хаб -> ALL] hub = EEAETB6…, addr tcp://192.168.1.140:22000`.
4. **КАЖДЫЙ ПИР (на своей стороне):** впиши хаб = verified ID, верный адрес, **удали устаревший ID**, рестарт демона штатным сторожем, → рапорт `connected` / что мешает.
5. **ПРОВЕРЬ:** `connections` все green; бэклог качается (`needFiles` падает).
6. **POST-MORTEM:** запиши корень, обнови реестр/реглумент. Если всплыл новый класс граблей — в Библию.

**Анти-грабли (выучено кровью):**
- Не доверяй ОДНОМУ пиру в диагнозе идентичности — у него может быть устаревшая запись (ноут уверенно звал «верни 2KPYBY4» — это сломало бы [коллега]). Источник истины = живой API хаба.
- Не пере-паривай всех на новый ID вслепую и не откатывай на старый, если кто-то уже работает на новом.
- Сторож с подозрением на «зависание» — сначала проверь СЛОЙ ВИДИМОСТИ (логи/ключ/403), а не ядро (verify-existing-before-proposing [internal]).

## 5. ПОЛИТИКА КАНАЛОВ (решения Антона, 2026-06-26)
**Вопрос 1 — когда используем Telegram? ВСЕГДА параллельно инбоксу?** → **ДА, ВСЕГДА параллельно**, но УМНО (не дублируем каждое сообщение = шум):
- **`[шина]` (Syncthing)** = дефолт для обычного/структурного/объёмного трафика, КОГДА синк жив.
- **Telegram-шина** = ВСЕГДА-онлайн для: **(а) HEARTBEAT** — каждая машина периодически (напр. ежечасно) постит `🤖 [машина -> ALL] alive @HH:MM` → канал всегда «тёплый», смерть синка/тишина пира видна СРАЗУ, и люди видят живость; **(б) ВЕСЬ трафик, когда синк лёг;** **(в) критическая координация/решения** (человеко-видимые).
- **Почему «всегда», а не «только когда синк лёг»:** если включать резерв лишь по факту аварии — не заметишь аварию, пока он не понадобился. Постоянный heartbeat = резерв всегда проверен + авария детектируется мгновенно. **AK-47-баланс:** всегда-параллельно для heartbeat+критики, НЕ дублировать каждое рутинное сообщение.

**Вопрос 2 — входящие в Telegram как КРОН/триггер?** → **ДА, отлично.** Входящее сообщение шины = **событийный триггер** (у Telegram-MCP есть `wait_for_settled_message` — событийное ожидание с дебаунсом). Это строго лучше поллинга: пир запостил → **немедленно будит inbox-робота**, а не ждём 20-мин опрос. Реактивность вместо задержки. *(TODO — повесить лёгкий слушатель / робота на `wait_for_settled_message` параллельно 20-мин расписанию.)*

**Итоговая лестница (канон — §4 [[reglament-multi-machine-claude-i-peredacha-mezhdu-mashinami]]):** `[шина]` (норма) → **Telegram `/bus` (FALLBACK #1, ВСЕГДА-параллельно: heartbeat+критика+триггер)** → e-mail (FALLBACK #2, TBD) → курьер-человек.
