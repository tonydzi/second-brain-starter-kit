# Telegram-шина: не зависеть от MCP + у каждой машины СВОЯ сессия

> Заказ Антона (2026-06-26, дословно): «ДЕЛАЙ!! это надо в библию!!» — по поводу того, что Telegram-MCP постоянно отваливается, а я построил MCP-независимый рельс шины и предложил корень-фикс (своя TG-сессия на каждую машину). Для всех акторов (Антон + ассистенты + AI). Связано с [[reglament-multi-machine-claude-i-peredacha-mezhdu-mashinami]] (§4 лестница каналов), [[reglament-chp-poterya-sinka-mezhdu-mashinami]], памятью machine-bus-telegram-rail [internal]. Подчиняется fix-root-cause-not-symptoms [internal].

## 0. TL;DR
- **Симптом:** Telegram-MCP (chigwell, `[путь владельца]`) регулярно «отваливается» — инструменты telegram пропадают из сессии, нельзя ни читать, ни писать в клан-шину.
- **КОРЕНЬ (из лога MCP, не гадаем):** `AuthKeyDuplicatedError` — *«сессия использовалась с двух разных IP одновременно и больше недействительна»*. ОДНА Telegram-сессия (один и тот же session-string / auth-key аккаунта `[рабочий аккаунт]`) живёт **сразу на нескольких машинах клана** (она лежит в СИНКАЕМЫХ файлах → расползается на все). Telegram видит один ключ с 2+ IP → считает это угоном → **гасит ключ** → MCP падает. Это тот же класс, что правило «НИКОГДА не копировать `.claude.json` между машинами».
- **Два правила-лечения:** (1) **шина не зависит от MCP** — читаем и пишем через лёгкий Telethon-рельс; (2) **у каждой машины СВОЯ Telegram-сессия** (свой auth-key/девайс), синкаемый общий session-string запрещён.

## 1. Правило A — клан-шина НЕ зависит от Telegram-MCP (resilient transport)
MCP — это удобство, а НЕ «жизненный нерв» шины. Шина обязана работать без него.
- **Читать шину:** `python %USERPROFILE%\.claude\scripts\tg_bus_read.py` — берёт группу `[REDACTED-SENSITIVE-ID]` по Telethon-рельсу (@[рабочий аккаунт]), показывает новое для ЭТОЙ машины (`▶ TO-ME` = адресовано мне/ALL) + контекст последних сообщений, машинно-локальная метка last-seen, `errors='replace'` (не падает на битом символе).
- **Писать в шину:** `python %USERPROFILE%\.claude\scripts\tg_bus_send.py --to <машина|ALL> "текст"` — авто-обёртка `🤖 [<моя-машина> → <dst>] текст`. `--raw` для готовой строки.
- **Авто-чтение на старте:** `tg_bus_read.py` вшит в SessionStart-хук (`inbox_hook.cmd`) рядом с Syncthing-инбоксом — каждая сессия видит ОБА ящика (Syncthing `[шина]` И Telegram), не только то, что приедет синком.
- Общий лок `_refresh_[рабочий аккаунт].lock` (как у `bus_ping.py`) → нет `AUTH_KEY_DUPLICATED` от пересечения процессов на ОДНОЙ машине.
- **Правило:** «MCP телеги упал» ≠ «шина легла». Падает MCP → молча переходим на `tg_bus_read`/`tg_bus_send`. Скилл bus [internal] и `tg_bus.py` тоже должны уметь fallback на этот рельс, когда MCP недоступен.

## 2. Правило B — у КАЖДОЙ машины своя Telegram-сессия (корень-фикс AuthKeyDuplicated)
- **Запрещено:** держать ОДИН session-string / auth-key Telegram-аккаунта в СИНКАЕМОМ файле (`.env`, `.claude.json`, конфиг MCP), который расползается на все машины. Один ключ на 2+ IP = Telegram его гасит. Это тот же инвариант, что «не копировать `.claude.json` между машинами».
- **Надо:** каждая машина логинится в Telegram **отдельно** (свой session-string = свой «девайс»). Telegram спокойно допускает МНОГО девайсов на один аккаунт — ломается только при копировании ОДНОГО ключа. Тег `🤖 [src → dst]` всё равно опознаёт машину, так что аккаунт-постер может быть и общий (`[рабочий аккаунт]`), но **session-string у каждого свой**.
- **Альтернатива (проще, если своя сессия дорога):** ОДНА всегда-вкл машина (хаб) = единственный MCP-постер; остальные читают/пишут только через свой Telethon-рельс.
- **Касается обоих рельсов:** и MCP-аккаунта, и REFRESH-сессии Telethon-рельса (`[путь владельца]`) — синкаемый общий REFRESH_SESSION_STRING несёт тот же латентный баг; развести по машинам.

### 2.1 Runbook FIX B — «дать машине свою сессию» (проверено на ноуте HP17, 2026-06-27)
Принцип: один StringSession = один auth-key, «размножить» нельзя → машина должна **залогиниться один раз**, и её сессия хранится **машинно-локально** (`%LOCALAPPDATA%\claude-tgbus\session.env`), НЕ в синкаемом `.env`.
1. **СНАЧАЛА измерь, есть ли проблема** (не делай лишних логинов): на каждой машине `python "%USERPROFILE%\.claude\scripts\tg_session_fingerprint.py"` → строка `REFRESH src=... sha=......` (печатает только last-8+sha, секрет не светит → безопасно слать в шину). Сравни sha по машинам: **все разные → сессии уже разведены, ничего делать не надо**; **совпали у 2+ → тем машинам нужна своя сессия.**
2. **Развести совпавшие:** на машине `python "%USERPROFILE%\.claude\scripts\tg_session_init.py"` — делает свежий логин выбранного аккаунта (по умолчанию `REFRESH`=@[рабочий аккаунт]), **сам забирает код входа из служебного чата 777000** через существующую сессию ([[reglament-ispolzuy-i-hrani-paroli-antona-ty-menedzher-paroley]], telegram-otp-self-fetch [internal]), 2FA-пароль берёт из `secrets\telegram_2fa.env` (ключ `TELEGRAM_2FA_<ACCT>`; @[рабочий аккаунт] 2FA **есть и хранится**). Пишет НОВЫЙ string в локальный файл. Секрет нигде не печатается (только отпечаток). Существующая синканная сессия остаётся валидной → другие машины НЕ задеты. **Для MCP-аккаунтов (Правило B «оба рельса»):** тот же инструмент с `--account [рабочий аккаунт]` (или `[рабочий аккаунт]`) — пишет НЕ в локальный override, а **в конфиг MCP `[путь владельца]`** (ключ `TELEGRAM_SESSION_STRING_<ACCT>`, с авто-бэкапом `.bak-<ts>`); MCP не запущен пока лежит → правка безопасна; **после правки нужен перезапуск Claude Code**, чтобы MCP подхватил новую сессию. Проверено на HP17 2026-06-27 ([рабочий аккаунт] 8734a4→270b8b).
3. **Рельс подхватывает сам:** `tg_bus_read.py` / `tg_bus_send.py` (и через них heartbeat) сливают локальный override ПОВЕРХ синканного `.env` (локальный выигрывает) → как только у машины появилась своя сессия, она используется автоматически.
4. **Проверь:** снова `tg_session_fingerprint.py` → `src=LOCAL-override` с НОВЫМ sha; одна отправка в шину = рельс на новой сессии жив.
5. **Только после развязки** включать частый пульс (25-мин heartbeat) на ВСЕ машины — иначе общий ключ с N IP снова словит AuthKeyDuplicated.
- **Единственный человеческий блок:** если 2FA-пароля аккаунта нет в store — попросить Антона (логин из чужой машины не сделать). Всё остальное — автономно.

## 2A. Как ПРАВИЛЬНО залогинить КАЖДУЮ машину «оригинально» (procedure — DR-validated 2026-06-27)
> Подтверждено внешним Deep Research (Альфа-Протокол, отчёт `deep-research-report (13)`). Канон-выбор: **мультисессия одного аккаунта** (не отдельный аккаунт на машину) — для малой команды это сохраняет ОДНУ идентичность/историю и проще всего; «оригинально» = каждая машина делает СВОЙ вход и хранит ключ ЛОКАЛЬНО.

**Принцип (почему это работает):** один Telegram-аккаунт спокойно держит МНОГО одновременных сессий — но каждая обязана быть СОЗДАНА своим отдельным входом (свой `auth_key`). `AuthKeyDuplicated` = не «много устройств», а ОДИН ключ, работающий с 2+ IP сразу. Значит лечение = у каждой машины свой вход + ключ хранится там, куда синк/копирование не дотянется.

**Процедура на каждой машине (по очереди, не разом):**
1. **Свой вход прямо на этой машине** — сгенерить свежий `StringSession` локально: движок `[путь владельца]` (QR) или `session_string_generator.py` (phone+code, 2FA-aware). Вход делает **оператор на месте** (SMS/2FA нельзя получить с чужой машины). ⚠️ Логины лимитированы (~5/сутки на номер) → не дёргать.
2. **Ключ кладём ТОЛЬКО в машинно-локальное, НЕ синкаемое место.** Корень бага = ключ лежал в СИНКАЕМОМ файле (волт `[путь владельца]`, `~/.claude`, или скопированный конфиг) → расползся на все. Правильные дома: Windows — Credential Manager / `keyring` / файл в `%LOCALAPPDATA%` (вне Syncthing, в `.gitignore` и в Syncthing-ignore); macOS — Keychain (`security add-generic-password`) / `~/Library/Application Support/...` с `chmod 600`. MCP-`.env` (`[путь владельца]`) годится, ЕСЛИ путь точно вне синка. REFRESH-строку рельса из синкаемого `[путь владельца]` — **увести в машинно-локальный путь** (это реальная текущая утечка).
3. **НИКОГДА не копировать `StringSession` между машинами** и не класть в: синкаемый волт, `~/.claude`, `.claude.json`, git, исходящие сообщения. Каждая машина = свой вход с нуля.
4. **api_id/api_hash можно общие** — они НЕ влияют на коллизию (изоляция на уровне сессии, не приложения). Отдельный api_id на машину НЕ нужен.
5. **Держим ≲5 одновременных сессий на аккаунт**, по возможности стабильный IP на машину, без частой пере-логинки и «прыжков» по странам — иначе анти-абуз может потребовать SMS-переверификацию (домашний IP в человеческом темпе = ок, прокси для своих аккаунтов не нужен — telegram-multiaccount-warm-maintenance [internal]).
6. **Проверка после:** `list_accounts`/`get_me` в сессии + детерминированный `/tg-check` (скрипт `tg_channels_check.py`) — оба канала 🟢.

**Восстановление (сессию всё же убили):** поймать `AuthKeyDuplicatedError`/`SessionRevokedError` → удалить мёртвый ключ → пере-логин ЛОКАЛЬНО. Полностью без человека НЕ выходит (нужен код из SMS + 2FA-пароль); код по возможности забираем сами из чата 777000 (telegram-otp-self-fetch [internal]), 2FA-пароль — из стора (credential-store [internal]); иначе алерт оператору.

**Альтернатива (если своя сессия на машину дорога):** ОДНА всегда-вкл машина (хаб) = единственный MCP-постер; остальные читают/пишут через свой Telethon-рельс или шину. Убирает коллизию полностью (одна сессия в мире), но хаб = единая точка отказа. Берём, когда нужна максимально простая телеграм-площадь.

## 3. Вторичные грабли (из лога) — добить
- `TypeNotFoundError: Could not find a matching Constructor ID` — **устаревшая Telethon** в `[путь владельца]`: Telegram обновил протокол, библиотека не знает новый объект. Фикс: обновить `telethon` в venv MCP.
- `PeerFloodError: Too many requests` — слишком частые отправки одним аккаунтом. Фикс: не флудить, батчить, паузы.
- `Unknown account '[рабочий аккаунт]'` — MCP знает аккаунты `[рабочий аккаунт], [рабочий аккаунт], default`; `@[рабочий аккаунт]` доступен ТОЛЬКО через Telethon-рельс (`REFRESH_*`), не через MCP-параметр `account`.

## 4. Runbook «MCP телеги отвалился»
1. **Не паниковать, шина жива:** читать `tg_bus_read.py`, писать `tg_bus_send.py` — MCP не нужен.
2. **Диагноз:** глянуть хвост лога `[путь владельца]` (или рядом). `AuthKeyDuplicated` → корень = общая сессия на 2+ машинах (Правило B). `TypeNotFound` → устаревшая Telethon (§3).
3. **Реконнект MCP:** stdio-MCP держит харнесс Claude Code; из сессии не переподнять. Действие = **перезапустить Claude Code** (харнесс заново поднимет MCP). Это ПЛАСТЫРЬ: при общей сессии снова словит AuthKeyDuplicated.
4. **Durable:** довести Правило B (своя сессия на машину) — иначе симптом вернётся (fix-root-cause-not-symptoms [internal]).

## 5. Границы (Tier-2)
- Развод TG-сессий по машинам и смена MCP-конфига = мульти-машинное изменение → координировать с хабом (канон-коммиттер), каждая машина логинится у себя (нужен оператор/Антон на месте). Из чужой машины это не сделать.
- Секреты сессий (session-string) хранятся как доступы ([[reglament-ispolzuy-i-hrani-paroli-antona-ty-menedzher-paroley]]), НЕ в исходящие/публику/always-loaded слой.
