> **Правило Антона (2026-06-28, «в библию!»).** При ЛЮБОЙ кросс-машинной синхронизации (git-транспорт, Syncthing, файл-шина) разделяй «конфиг/секреты» на ДВА класса и обращайся с ними ПРОТИВОПОЛОЖНО. Машинно-специфичное шарить **ГЛУПО и ОПАСНО — не из-за приватности, а потому что оно ЛОМАЕТСЯ.**

## Два класса — лечим наоборот

| Класс | Примеры | Шарить? | Почему |
|---|---|---|---|
| 🟢 **ОБЩЕЕ** (одно на всех) | `CLAUDE.md`, `MEMORY.md`+`memory/*.md`, скиллы, пароли аккаунтов, API-ключи, 2FA, `credential-store` | **ДА, свободно** | все машины логинятся в ОДНИ аккаунты — поменял раз, у всех. Приватность не барьер (машины Антона все приватные). |
| 🔴 **ПАСПОРТ МАШИНЫ** (у каждой своё) | `settings.json` (свои MCP/пути/хуки), Syncthing `*.pem` (уникальный ID узла), Telegram session-строки | **НЕТ — только локально** | это не «секрет», это ПАСПОРТ конкретной машины |

## А чем возить 🟢 ОБЩЕЕ: Git (3-way merge) vs Syncthing — ОДИН критерий

Syncthing **не умеет сливать текст**: если две машины правят один файл, он берёт «последний победил», а проигравшую правку молча кидает в `.sync-conflict` — твоя работа тихо откатывается (дымящийся пистолет: `CLAUDE.sync-conflict-…EEAETB6.md`). Git умеет слить обе правки. Отсюда решающий вопрос:

> **«Пишут ли в ОДИН текстовый файл НЕСКОЛЬКО машин одновременно?»** Да → **Git-транспорт** (git-daemon по LAN, 3-way merge). Нет → **Syncthing достаточно**.

| Файлы | Несколько писателей? | Транспорт |
|---|---|---|
| 🟦 `MEMORY.md`, `memory/*.md` | **ДА** (любая сессия любой машины) | **Git — обязателен** (`claude-memory.git`) |
| `CLAUDE.md` | Нет — канон коммитит только хаб (Вожак) | Git как лёгкая страховка (`claude-claudemd.git`); коллизий нет |
| 🟩 **скиллы** | Почти нет — правит хаб, followers receive-only | **Syncthing** (шара `claude-skills`) |
| 🟩 волт `[путь владельца]`, `_imports` (`.db`), `secrets` | — (большой / бинарь / не-offsite) | **Syncthing** (git-враждебны / слишком большие) |

⚠️ Не путать **две роли Git**: (1) Git-**бэкап** = 15-мин авто-коммит на КАЖДОЙ машине локально, ничего не возит между машинами, страхует от потери (claude-skills-git-backup [internal]); (2) Git-**транспорт** = git-daemon, возит и сливает между машинами. Транспорт нужен ТОЛЬКО для memory; всё прочее общее едет Syncthing'ом, а git-бэкап страхует его локально.

## Почему паспорт нельзя класть в общий репо (механика, не лень)

В общей линейной git-истории на вершине лежит ОДНА версия `settings.json`. Кто подтянет (pull / fast-forward) — тому она НАВЯЖЕТСЯ, и его собственный конфиг затрётся/сломается. Пометка `merge=ours` спасает только настоящий *конфликт* (обе машины правили один файл), но НЕ односторонние правки и НЕ fast-forward → её **недостаточно**. Единственный безопасный дизайн: держать паспорта ВНЕ общего репо целиком — `git rm --cached` + `.gitignore`, каждая машина хранит свой в локальном бэкапе.

## Живое доказательство (тот же день)

Telegram-рельс хаба умер с `AuthKeyDuplicatedError`, потому что ОДНУ Telegram-сессию засинкали на 2 машины → два узла с одним паспортом → Telegram их выкидывает. Это ровно то, что делает шаринг идентичности.

## Как применять

- Поднимаешь кросс-машинный канал → ОБЩИЙ текст/креды в общий репо; `settings.json` / `*.pem` / `*.session` → `git rm --cached` + `.gitignore`, остаются в ЛОКАЛЬНОМ пер-машинном бэкапе.
- Репо с историей, где когда-то лежали `.pem`/секреты, **НИКОГДА не пушим в облачный fallback** (инвариант «секреты не offsite» в силе); локальный шаринг между машинами Антона — ОК.
- Telegram: каждая машина логинится в СВОЮ локальную сессию (`tg_session_init.py --account`), общую session-строку не синкаем.
