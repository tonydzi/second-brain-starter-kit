# Реглумент: миграция на новую машину (сотрудник / сын / новый Mac)

> Для ВСЕХ акторов (Антон + живые ассистенты + AI). Это **тонкий указатель** — вся механика и полный
> каталог грабли живут в одном источнике: [[journal-migration-laptop-to-hub]] (не дублируем, чтобы копии
> не разъезжались). Этот реглумент = «что делать по шагам и чего НИКОГДА не делать».

## Когда применять
Поднимаем единую систему Claude+волт на новой машине: компьютер сотрудника, сына, новый Mac, замена ноута.

## Порядок (коротко — детали в журнале §4)
1. **На источнике, в день переезда:** пере-экспортировать задачи; пере-собрать чемодан; перечислить
   коннекторы по `.claude.json → mcpServers` (НЕ по бэкапу волта).
2. **ШАГ 0 на новой машине:** убедиться, ГДЕ ты (модель/GPU/диски) — раньше «десктоп» оказывался ноутом.
3. **Распаковка по фазам A→G** (`NEW-SESSION-RUNME.md`): база → конфиг+память → волт → коннекторы
   (каждый MCP = рестарт Claude) → Python/RAG → задачи → проверка.
4. **Syncthing на свежей машине:** Receive-Only → **Revert Local Changes** → Send&Receive (иначе
   устаревшая машина затрёт свежую). Демон — авто-старт через VBS, не через сессию Claude.
5. **Передать файл между машинами** — только синкаемый канал `[шина]\_transit\`. НИКОГДА не
   рассчитывать, что `_imports` / `_cowork-inbox` / live-`hooks` / скрины-вне-волта сами доедут.

## Жёсткие «НИКОГДА» (нарушение = потеря данных)
- ⛔ НЕ копировать `.claude.json` между машинами → `AUTH_KEY_DUPLICATED` убивает Telegram/WhatsApp (логин заново).
- ⛔ НЕ держать `.git` волта в Google Drive / iCloud / OneDrive — облако ломает репозиторий.
- ⛔ `_originals\` — только копировать, никогда не удалять/менять.
- ⛔ НЕ синкать venv / node_modules / RAG-индекс между ОС — ставится/пересобирается заново.
- ⛔ НЕ ставить MongoDB — мёртвый sandbox-коннектор; наш стек = SQLite.
- ⛔ 2FA-пароли (Telegram cloud и пр.) нигде не хранить — только у владельца.

## Машины КОЛЛЕГ/семьи — что НЕ ставим (Anton, 2026-06-22)
Новой машине коллеги/члена семьи даём **общий стек** (волт-синк, конфиг, скиллы, RAG), но **НЕ** личные привязки Антона:
- ⛔ **Telegram-read-сессии аккаунтов Антона** ([рабочий аккаунт] / [рабочий аккаунт] / TONYDZI и пр. в `dialogs\.env`) и зависящие от них роботы (**CRM Engine Fields Sync** и т.п.) — это **ТОЛЬКО на десктоп-ХАБ** (всегда-вкл, личная машина Антона). Коллеге читать аккаунты Антона незачем + лишняя device-сессия = риск. Заводятся **свежим логином** на хабе (НЕ копией сессии → иначе `AUTH_KEY_DUPLICATED`).
- ⛔ Аналогично — device-bound коннекторы Антона (WhatsApp/Baileys, его OAuth-keychain). У коллеги — свои аккаунты, не Антона.
Правило: «личное Антона → только его машины (хаб/ноут); общий стек знаний → всем». Канон-факт привязок: telegram-otp-self-fetch [internal], whatsapp-mcp-integration [internal].

## Машина ведомого: канон-папки = receive-only (Anton, 2026-06-22)
Машина коллеги/семьи — **ведомая** (см. [[reglament-vozhak-vedomyy-canon-governance]]). При онбординге:
- Канон-папки ведомого (`claude-home` = CLAUDE.md+hooks+commands; папка Библии в волте) выставить
  **receive-only** в Syncthing → ведомый ПОЛУЧАЕТ канон вожака, локальные правки авто-откатываются.
- Объяснить Claude на ведомой: канон ты **ПРЕДЛАГАЕШЬ** (`[шина]/_transit/canon-proposals/` + пинг
  хаба `[машина флота]`), не пишешь напрямую. Всё своё (скиллы/скрипты/работа) — делаешь сам, без гейта.
- Подача не унизительная: «канон ждёт ратификации Антоном/хабом, чтобы закон не разъезжался».

## Урок №1 (почему вообще завели этот журнал)
**Скиллы / хуки / скрипты, которые лежат вне 4 синкаемых папок, на новую машину НЕ попадают сами.**
Симптом «скиллы не доехали» (21.06) = скиллы ехали только backup-копией без живого моста. Фикс —
live-синк папки `~/.claude/skills` (как память). Что синкается, а что нет — таблица в журнале §2.

## Шаг онбординга: сторож Syncthing + мгновенный триггер на пробуждение (2026-06-23)
Грабли, ради которых: машина засыпает, Syncthing встаёт «застрявшим» (процесс жив, 0 пиров, API 403),
и это выглядит как «инбокс/шина между машинами сломались», хотя сломан только синк. На КАЖДОЙ
Windows-машине клана ставим самолечащийся сторож (0 токенов, чистый PowerShell, файлы уже едут в
синкаемой `[путь владельца]`):
1. **Медленная страховка** (раз в 57 мин): скопировать `start-syncthing-watchdog.vbs` в папку Startup
   (`%AppData%\Microsoft\Windows\Start Menu\Programs\Startup`). Тянет `syncthing_watchdog_loop.ps1` →
   `syncthing_watchdog.ps1`: если пиров `<1`, делает kill+relaunch с кулдауном; не чинится → пинг через
   `alert_fallback.py`. Без админ-прав.
2. **Мгновенный триггер** (главный, ловит «застрял после сна» за секунды): один раз запустить
   `install-syncthing-watchdog-onwake.ps1` **от администратора** (правый клик → «Запуск от
   администратора», либо из сессии Claude `Start-Process -Verb RunAs` → выскочит UAC, нажать «Да»).
   Регистрирует задачу `SyncthingWatchdogOnWake` на события resume-from-sleep + unlock. Установщик
   резолвит путь к сторожу через `$PSScriptRoot` → правок под машину НЕ требует (потому и кладём в синк).
3. **Mac (TODO):** эквивалент = LaunchAgent на wake (`sleepwatcher` / `pmset -g log`); у Антона Маки тоже
   в клане, поднять при первом Mac-онбординге.
