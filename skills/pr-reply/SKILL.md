# /pr-reply — ответить тем, кто уже согласился с нами разговаривать

## Закон
**Молчание в живом треде = провал, а не осторожность** (CLAUDE.md §4.7). Отвечаю САМ: GitHub
выведен из-под гейта Наташи, «+» Антона не жду. Порог — **24 часа**.

Живой ревьюер дороже нового PR. Человек, который написал на нашем PR, уже потратил своё
время — это самая тёплая дверь, какая у нас есть, и она закрывается от молчания, а не от
несогласия. Спорить с ним можно и нужно ([[objection-sparring-to-consensus]]), молчать — нет.

## Шаг 1 — снять очередь (0 токенов, 0 своей сети)
```
python ~/.claude/scripts/pr_watch.py --digest
```
Секция **🔴 МЯЧ У НАС** — это и есть очередь. Дальше глазами раздели её на три кучи:

| Кто говорил последним | Что делаем |
|---|---|
| **живой человек** | работаем сегодня, начиная с самого старого |
| **бот** (`codecov[bot]`, `cubic-dev-ai[bot]`, `review-notebook-app[bot]`, `chatgpt-codex-connector`) | чиним, если по делу; отвечать текстом не нужно |
| ⏳ **STALE/CLOSE-бот** (`github-actions[bot]`: «This PR is stale…», «will be closed in N days») | **ИСКЛЮЧЕНИЕ ИЗ СТРОКИ ВЫШЕ: текст ОБЯЗАТЕЛЕН и он же есть лекарство.** Коммент — единственное, что снимает ярлык и обнуляет счётчик (`actions/stale` по умолчанию держит `remove-stale-when-updated: true`). Молчание = удаление артефакта в объявленный срок. Писать СОДЕРЖАТЕЛЬНО: что закрыто по ревью · чем дешево ревьюить (что идёт в CI без ключа) · предложение ребейзнуть или подвинуть. Голый «bump» ⛔ (§1.5 спам ≠ громкость). Дату смерти брать фактом: `gh api repos/<o>/<r>/contents/.github/workflows/stale.yaml` → `days-before-pr-stale` + `days-before-pr-close`; конфига нет = «бота нет» (это claim, бессрочность не выдумывать). Живой случай 30.09: `openai/openai-cookbook#2880`, 74k звёзд, до удаления оставалось 7 дней, три прогона вахты промолчали — все три двери (`pr_watch.py` · вахта тредов · эта таблица) считали бота шумом. |
| 🔧 **INTAKE-бот с МЕХАНИЧЕСКИМ флагом** (`graphiti-intake-bot` и родня: «нужен linked issue `Fixes #<N>`», «нужна метка», «отметьте пункт чек-листа», «заполните шаблон») | **ЛЕЧИТСЯ ПРАВКОЙ АРТЕФАКТА, А НЕ КОММЕНТОМ.** Флаг снимает `gh pr edit <N> --body-file` / `--add-label` / правка заголовка — бот перечитывает PR на своём прогоне и гасит метку сам, в треде НОЛЬ шума. Коммент сюда = бамп (§1.5). Проверка, что сработало: метка-флаг ИСЧЕЗЛА (`gh api repos/<o>/<r>/issues/<N> --jq '[.labels[].name]'`) — это независимый сигнал, а не наш claim. ⚠️ Ключевое слово `Fixes #N` ЗАКРЫВАЕТ issue на мерже: наш PR = часть issue → ставим слово (бот требует буквально его) И рядом scope-строку «это подмножество, снимите ключевое слово на squash или переоткройте», выбор отдаём мейнтейнеру, молча чужой issue не хороним. Живой случай 02.10: `getzep/graphiti#1810`, часы до 15.10, флаг `needs-issue` снят правкой тела за один вызов. |
| 🤖 **СИНТЕТИЧЕСКИЙ ПИР БЕЗ СУФФИКСА `[bot]`** (`<имя><цифры>-coder` / `-code` / `-lang` и родня: `qaisermehdi3-coder`, `juancarlosrial76-code`, `eddyflores100-lang`) | **ЭТО НЕ ЖИВОЙ ЧЕЛОВЕК, И В ЧУЖОМ ТРЕДЕ ОТВЕТ ЕМУ = ШУМ МЕЙНТЕЙНЕРУ.** Строка выше («боту отвечают коммитом») ловит только логин с `[bot]`; эти аккаунты проходят фильтр как люди и приносят полированный LLM-текст через часы после нашего коммента. Дешёвая проба ОДНИМ вызовом перед ответом: `gh api users/<login> --jq '[.created_at,.public_repos,.followers,(.bio//"-")]'` — молодой аккаунт + `public_repos<=2` + `followers<=1` + пустой bio = синтетический пир (живой мейнтейнер для сравнения: `dsfaccini` 2020 год, 70 репо, 46 фолловеров, bio). В ЧУЖОМ треде такой коммент долгом НЕ является, отвечаем только когда обращается мейнтейнер или автор. Живой случай 03.10: `pydantic/pydantic-ai#8704` — мы ответили `qaisermehdi3-coder` коммент-в-коммент, и через 2 минуты assignee `dsfaccini` написал «bots: please refrain from replying to each other, we've got enough input here»; четвёртый коммент за 13 часов в треде, который мейнтейнер держит чистым. Журнал: класс `reply-to-synthetic-peer-in-foreign-thread`, 1-й датированный случай. |
| **«нет снимка»** | почти всегда позиция, добавленная СЕГОДНЯ нами же — см. блок ниже ДО любых сетевых вызовов |

### ⚠️ «Нет снимка» ≠ долг: сперва реестр, потом сеть (замер 27.09)
Позиция попадает в 🔴 без снимка просто потому, что сторож её ещё не видел, а `--add` был сегодня.
Дешёвый разбор — 0 сетевых вызовов, по самому реестру `_outreach/outbound_github.json`:
```
python3 -c "import json;d=json.load(open('$OBSIDIAN_VAULT/_outreach/outbound_github.json'));\
print('\n'.join('%s#%s kind=%s added=%s :: %s'%(i['repo'],i['number'],i.get('kind','issue'),i.get('added'),i.get('note','')[:70]) for i in d['prs'] if i.get('added')=='<сегодня>'))"
```
Две вещи, которые эта строка отдаёт даром:
- **`added` = сегодня + note «ответ … ждём реакции»** → мяч у НИХ, это наш собственный свежий ответ. Не долг, сеть не нужна.
- **`kind: discussion`** → у дискуссий НЕТ `repos/<o>/<r>/issues/N`, REST вернёт 404 на всё подряд.
  Дверь только GraphQL: `gh api graphql -f query='{repository(owner:"O",name:"R"){discussion(number:N){isAnswered updatedAt comments(last:2){nodes{author{login} createdAt}}}}}'`.
  ⚠️ В `zsh` не собирай такой цикл через `set -- $spec` — `$3` приезжает пустым и GraphQL падает
  на `discussion(number:)`; заведи `check() { … "$1" "$2" "$3" … }` и вызывай явно.

Замер 27.09: шесть позиций «нет снимка» → три дискуссии (REST дал 404, я списал это на мусор в реестре — неверно)
и три треда с нашим же ответом того же дня. Настоящий долг среди шести был **один** (наш PR с упавшим CI-ботом),
и он виден по `kind` + автору без единого запроса к GitHub.

#### ⚠️ Поправка 05.10: `note` бывает ПУСТОЙ, и тогда реестр отдаёт только `added` (замер: 17 позиций разом)
Эвристика выше опирается на `note` со словами «ответ … ждём реакции». В тот день она не сработала:
из 17 красных «нет снимка» **13 имели `note: None`**, потому что веер другого лейна узла добавил их
без заметки. Голого `added = сегодня` для вердикта мало — он не отличает «мы ответили» от «нас спросили».
Добирается ОДНИМ пакетным циклом (1 вызов модели на все позиции, не по одной):
```bash
for p in "owner/repo 123" "owner/repo2 456"; do R="${p% *}"; N="${p##* }"
  echo "$R#$N by=$(gh api repos/$R/issues/$N --jq '[.user.login,(.pull_request!=null|tostring)]|join("|")') \
last=$(gh api repos/$R/issues/$N/comments?per_page=100 --jq '.[-1]|[.user.login,.created_at]|join("|")')"
done
```
Вердикт читается механически: `last = tonydzi` сегодня → **не долг** (наш свежий коммент) · `last` пустой
→ наш PR без комментов, **не долг** · `last` = `*[bot]` → **не долг** · `last` = живой человек → в разбор.
В тот заход так закрылись 17 позиций, и настоящие долги пришли не отсюда, а из `mentions`/`involves` (блок ниже).
⚠️ Цикл писать на `bash` с массивом (см. предупреждение про `set -- $spec` в `zsh` выше).

⭐ **КАК ДЕЛАТЬ ДОБОР ОДНИМ ВЫЗОВОМ (замер 22.09, 5-й случай класса подряд).** Проверять последнего
комментатора по 40–60 позициям REST-парами — это ~110 сетевых вызовов; один GraphQL с алиасами даёт
то же за один. Шаблон: на каждую позицию `aN: repository(owner:"o", name:"r"){ issueOrPublicRequest…}`,
внутри `issueOrPullRequest(number:N)` с двумя инлайн-фрагментами (`... on Issue` / `... on PullRequest`),
в каждом `comments(last:1){ nodes{ author{login} createdAt } }`. `comments(last:1)` снимает всю возню
с пагинацией: GraphQL сам отдаёт ХВОСТ, грабля `.[-1]` первой страницы к нему не относится.
Два условия, иначе прибор соврёт: (1) `gh api graphql` возвращает **ненулевой код при ЧАСТИЧНЫХ ошибках**
(позиция оказалась discussion → «Could not resolve to an issue or pull request»), но `data` в stdout
при этом ЕСТЬ — парсь stdout, не выходи по returncode, иначе одна discussion гасит все 55 позиций;
(2) сравнивай логин с `tonydzi` явно — «наш последний» и «их последний» это и есть весь вердикт.
Замер 22.09: 4 красных дали 2 настоящих долга, а ещё 4 (`claude-agent-sdk-python#1276`, `#1271`,
`mem0#6859`, `hermes-agent#88371`) стояли зелёными или в «чужих тредах».

⛔ **ВТОРАЯ ГРАБЛЯ ТОГО ЖЕ ПРИБОРА (замер 21.09): `.[-1]` БЕЗ ПАГИНАЦИИ ВРЁТ НА ДЛИННОМ ТРЕДЕ.**
Эндпоинт `GET /repos/{o}/{r}/issues/{N}/comments` **игнорирует `sort` и `direction`** (в его контракте
их просто нет — только `since`, `per_page`, `page`), поэтому `--jq '.[-1]...'` отдаёт последний
коммент ПЕРВОЙ СТРАНИЦЫ, то есть №100, а не последний в треде. 21.09 так соврал `gastownhall/beads#5877`
(101 коммент): прибор показал «последним писал tonydzi», хотя реальный последний был от @The1nk
в тот же день, и тред чуть не уехал в «не долг». Чем людней тред — тем вероятнее ложь, а людные
треды мы берём ПЕРВЫМИ (§4.7 «самый людный живой тред домена первым»), так что грабля лежит
ровно на приоритетной дорожке.
Лечение — брать последнюю страницу явно:
```bash
cnt=$(gh api "repos/$repo/issues/$num" --jq '.comments')
page=$(( (cnt + 99) / 100 ))
gh api "repos/$repo/issues/$num/comments?per_page=100&page=$page" \
  --jq '.[-1] | .user.login + " @ " + .created_at'
```
Готовый вариант на список тредов (считает страницу сам, печатает 2 последних коммента):
`~/.claude/skills/pr-reply/gh_last_comment.sh <owner/repo#N> [...]` (живёт рядом со скиллом —
единственным потребителем; в `~/.claude/scripts` не кладём, там 21.09 висела чужая EXCLUSIVE-табличка
ON AIR на зоне `fleet-code`, и дверь `onair_fleet_guard.py` запись справедливо отбила).

### ⚠️ «Последний не мы» ≠ «ответ нам» (замер 14.09)
Digest ставит «ОТВЕТ ЗА НАМИ», если последним писал не tonydzi. В НАШЕМ PR это правда. В чужом
большом issue, где мы — один из 40 участников, это чаще посторонний, который пишет не нам.
Замер 14.09: из 53 позиций адресованы нам были 15; ещё ~25 — посторонние (anthropics/claude-code ×9 и
др.), 3 уже отвечены соседом, 6 ссылок 404. Прежде чем писать, прочитай последние 2–3 реплики: есть
`@tonydzi`, ответ на наш аргумент или просьба к автору/ревьюеру, которым были мы? Нет → не отвечаем,
ответ без новой ценности = спам (§1.5). Боты digest уже не считает (`is_bot` в `pr_watch.py`).
Leak-scan тела ответа: паттерны `repo_release_leakscan.py` (FAIL+WARN) по файлу `--body-file`, плюс
последняя строка обязана нести `github.com/tonydzi`.

### ⚠️ СОБЕСЕДНИК САМ ЗАКРЫЛ РАЗГОВОР — это не долг и не 🪦 (замер 24.09)
Третий вид ложного красного, отдельный от «пишут не нам». Мяч формально у нас, реплика адресована
НАМ и по существу — но её содержание есть **явный выход из разговора**: «letting this one rest» ·
«I'm going to stop here» · «I'd rather it sit finished» · «leaving it open for a maintainer» ·
«@maintainer PTAL» (пинг третьему лицу, а не нам). Ответ туда не несёт новой ценности и читается
как «мне нужно последнее слово».
Замер 24.09: из 8 красных ТРИ были такими (`BerriAI/litellm#34140` и `#41395` — DanBrima закрыл оба
одной парой реплик; `google/adk-go#1543` — wolo-lab пингует `@wojtas000`). Ещё одна —
осуждённый ранее `fieldkit#77`. Итого половина очереди дня.
Вердикт пишется в журнал В ТЕХ ЖЕ СЛОВАХ, что и осуждённые позиции Шага 1-бис, и работает так же:
позиция остаётся красной навсегда (у `pr_watch` нет mute — проверено `--help`), следующий заход
смотрит только, появился ли комментарий НОВЕЕ даты вердикта.
⭐ Граница: это НЕ повод молчать там, где человек закончил репликой **к нам** — благодарность с
техническим содержанием, поправка нашего аргумента, вопрос «а как бы вы сделали». Тест один:
после моей реплики у собеседника появится работа или знание? Нет — не пишем.

### ⚠️ Сначала спроси: чей это PR
Реестр держит **оба** направления, и работа в них разная. Проверяется одной командой:
```
gh pr view <N> --repo <owner/repo> --json author --jq .author.login
```

| Автор PR | Кто мы | Что от нас ждут |
|---|---|---|
| **мы** | автор | сделать правку, которую попросил ревьюер → шаги 3–4 |
| **посторонний** | ревьюер | перепроверить их фикс и вынести вердикт → шаг 3-бис |

Замер 06.08: из трёх живых людей в очереди **двое ждали нас как РЕВЬЮЕРОВ**, а не как
авторов. Спутать эти роли — значит прийти в чужой тред с «поправил, посмотрите», где от
нас ждали проверки. Роль определяется автором PR, а не тем, в чьём репозитории он открыт.

⚠️ Очередь ровно так же свежа, как снимки сторожа. Дата снимка печатается в шапке digest —
если она вчерашняя, очередь тоже вчерашняя. Не выдавай старый список за сегодняшний.

### 🪦 Правило трёх дней (anton «+» 07.08)

### ⭐ Мяч у НИХ, но протух НАШ собственный claim — это новая ценность, а не бамп (замер 19.09)
Могила и «ждём их» запрещают бамп без новой ценности. Но **наше опубликованное утверждение —
такой же скоропортящийся продукт, как и цифра** ([[prichina-kak-claim]]): версия вышла, тег
переехал, баг уехал в релиз. Проверка дешёвая и делается ДО решения «молчим»: то, что мы в этом
треде утверждали про версии/релизы/состояние — всё ещё правда СЕГОДНЯ?

Протухло → пишем, даже если формально отвечают они, и первым абзацем правим себя, а не
повторяем просьбу. Замер, родивший правило: в `google/adk-python#6941` мы 05.09 написали «ни один
опубликованный релиз не несёт `bfeb04c`» — 10.09 вышел `v2.9.0`, который его несёт, и баг из
«живёт на main» стал «стоит у пользователей». Проверка = две команды
(`gh api repos/<repo>/compare/<tag>...<sha> --jq .status` → `behind` значит содержится;
`gh api repos/<repo>/releases --jq '.[0:5][] | "\(.tag_name) \(.published_at)"'`).

⚠️ Граница: это НЕ лазейка для бампа. Новая ценность = факт, который изменился в мире и меняет
приоритет для мейнтейнера; «прошла неделя» и «напоминаю» ценностью не являются. Перепроверять
на опубликованном артефакте, а не на чекауте: `pip install <pkg>==<version>` + контрольный кейс,

## Шаг 3-бис — если ревьюеры МЫ: проверять доказательство, а не поведение
Автор написал «поправил всё по вашим замечаниям». Прогнать его тесты и увидеть зелёное —
**недостаточно**: зелёный тест доказывает, что тест проходит, а не что защита работает.

Порядок:
1. Забрать ветку: `git fetch upstream pull/<N>/head:pr<N> && git checkout pr<N>`.
2. Прогнать так, как автор говорит, и назвать точный способ прогона в ответе (какие ячейки,
   с сетью или без, какой python) — иначе вердикт невоспроизводим.
3. **Сломать по одной защите в РАБОЧЕМ коде, не трогая тесты, и убедиться, что тест краснеет.**
   Не поймал — защита есть только на бумаге, и это находка ценнее любого стилевого замечания.

⚠️ Грабли метода (наступил 06.08): мутация, которая переименовывает строку и в проверке, и в
тесте разом, «проходит» всегда — тест сравнивает переименованное с переименованным. Ломать
надо ПОВЕДЕНИЕ: убрать `return refused`, а не переименовать код ошибки. Первый прогон дал три
ложных «ПРОПУЩЕНА» именно из-за этого; сначала я усомнился в их коде, и был неправ.

⚠️ Вторые грабли: изолированный прогон пары ячеек не тянет импорты из ранних. `NameError` —

⚠️ Чужой РЕПРО (не PR) проверяй так же: у каждой строки вывода нужен контроль, который МОГ провалиться — негатив для «гейт вернул True» (гейт вообще умеет False?) и позитив для «операций 0» (у заведомо правильного случая они есть?). ## ⭐ Шаг 6-прим — ВЫЧИТАЙ ОТПРАВЛЕННОЕ ОБРАТНО С СЕРВЕРА, И СВЕРЯЙ ПО md5, А НЕ ПО ДЛИНЕ (пережито 04.10.2026)

`gh issue comment` печатает URL и выходит с 0 — это доказывает ПРИЁМ запроса, не целость тела.
Второй заход (§4.3-бис «другим способом, чем в первый раз») для исходящего коммента выглядит так:
взять `id` из URL и прочитать тело ОБРАТНО, а не пересказывать свой файл.

```

```

⚠️ **ЛОВУШКА, КОТОРАЯ ВЫГЛЯДИТ КАК ОБРЕЗАННЫЙ КОММЕНТ:** сверка по ДЛИНЕ даёт ложное
расхождение. `jq '.body|length'` считает **кодпоинты**, `wc -c` — **байты**; каждый em-dash
(`—`) в нашем тексте — 3 байта и 1 кодпоинт, то есть +2 байта расхождения на штуку.

потеря 15 символов, хотя md5 совпал байт в байт — 7 em-dash'ей (14) плюс перевод строки.
Длина как прибор здесь СЛЕПА; судит только md5 (или прямое сравнение строк).

Тело уехало битым — чиним, а не оправдываемся: `gh api -X PATCH repos/<o>/<r>/issues/comments/$ID -f body="$(cat "$F")"`.

## Как понять, что скилл работает
Считаем **не** число ответов, а возраст самого старого живого долга в digest. Работает —

а не повод отвечать быстрее.

## Шаг 3-кватер — REST отдал 403 «rate limit exceeded» при пустом счётчике → пиши через GraphQL (замер 07.10.2026, pr-reply-daily Mac16)
Симптом: каждый `gh api repos/...` отвечает `API rate limit exceeded for user ID …`, а `gh api rate_limit` при этом показывает `core.remaining=5000, used=0`.
✅ Причина доказана 08.10.2026: это ПЕРВИЧНЫЙ часовой бак аккаунта (текст вторичного лимита другой — «secondary rate limit»), съеденный тиком `pr_watch.py` 15:15 (658 тредов × 5 REST = ~3300/час) плюс соседями. Тело `/rate_limit` на этом токене СЛЕПО: каждый вызов отдаёт фантомное окно (`used=0`, `reset` = сейчас+1ч и ползёт). Настоящий бак — только по заголовкам живого ответа: `python3 ~/.claude/scripts/_shared/gh_budget.py`. Корень закрыт: `pr_watch` сперва спрашивает GraphQL-пачкой `updatedAt` и платит REST только за сдвинувшиеся треды (замер: 676 вместо ~3300), а на первом 403 останавливает тик; сторож `_test_gh_rest_limit.py`.
Дверь: GraphQL считается ОТДЕЛЬНЫМ баком (`graphql.remaining` живой) и умеет и читать хвосты (`issueOrPullRequest(number){ comments(last:4){…} }`, семь тредов одним запросом), и писать: `python3 ~/.claude/skills/pr-reply/gh_gql_comment.py <owner> <repo> <N> <body_file>` = mutation `addComment` + md5-сверка тела по readback (exit 0 только при MATCH). Инструмент лежит рядом со скиллом (единственный потребитель; `~/.claude/scripts` в тот вечер держал чужой ON AIR). Работает для issue и PR одинаково; гейты `paragraph_lint && leak_scan &&` ставятся перед ним той же цепочкой `&&`.
⛔ Не замена ревью: первое касание в чужой PR остаётся `gh pr review --comment` (REST); 403 на нём → ждать окно либо писать с другого узла, не подменять ревью комментом молча.
