## Шаг 1-бис — «последним сказал чужой» ≠ долг: разговор мог уехать в PR
Эвристика «последний говоривший в треде» ловит ДОЛГ и МИГРАЦИЮ одинаково, а это разные вещи.
Нормальный цикл выглядит так: человек пишет в issue «claiming this» или «I opened PR #N» — и
дальше по существу говорят уже в PR. В issue его строка так и остаётся последней НАВСЕГДА, даже
когда мы разобрали, отревьюили и смержили. Долга там нет, мяч не наш.

Поэтому на КАЖДЫЙ хит спрашиваю ещё один вопрос, прежде чем идти отвечать:
```
gh api "/repos/tonydzi/<repo>/issues/<N>/timeline" --paginate --jq '.[]|select(.event=="cross-referenced")|.source.issue.number'
gh api "/repos/tonydzi/<repo>/issues/<PR>/comments" --paginate --jq '.[]|"\(.user.login) @ \(.created_at)"'
gh api "/repos/tonydzi/<repo>/pulls/<PR>/reviews"   --paginate --jq '.[]|"\(.state) \(.user.login) @ \(.submitted_at)"'
```
Наш ответ в связанном PR ПОЗЖЕ его последней строки в issue = касание обслужено, хит закрыт.
⚠️ ЗАМЕР 21.09.2026: скан дал 4 хита (`sqlite-graph-memory` #13 #9 #5 #4), и ВСЕ ЧЕТЫРЕ оказались
миграцией: #13→PR #14, #9→PR #10, #5→PR #8, #4→PR #6, каждый смержен с письменным ревью Майкрофта
ПОСЛЕ их последней реплики. Долгов было 0. Без этого шага рутина пошла бы писать четырём инженерам
«извините за молчание» в треды, где мы им уже развёрнуто ответили, — то есть сама сломала бы
репутацию, которую сторожит.
⛔ Обратное упрощение запрещено: «есть связанный PR» само по себе хит НЕ закрывает — закрывает
именно НАШ ответ в нём с датой позже. Смерженный молча PR без единого нашего слова — это долг
(§4.7: молчание в живом треде = провал), и он идёт в Шаг 4 как обычное касание.

## Шаг 1-тер — ЗЕРКАЛЬНОЕ слепое пятно: долг бывает и там, где последними говорили МЫ
Оба скана Шага 1 спрашивают «кто сказал последним» и потому ловят ровно один вид долга — «нам
написали, мы молчим». Второго вида они не видят ВООБЩЕ: **мы пообещали и не сделали**. В таком
треде последняя строка наша, хит не возникает, прибор честно рапортует ноль — а человек ждёт.

⚠️ ЗАМЕР 27.09.2026, чем это стоило: три скана (комменты вкл. закрытые, чужие открытые, inline-ревью)
по 60 репо дали 0 долгов, и это была правда. Параллельно в `sqlite-graph-memory` PR#8 висело наше
обещание 15.09 — «the triage invite waits for Anton's click, you'll see it arrive from GitHub» —
данное человеку, который согласился («I would gladly accept») через час после предложения ещё 13.09.
Приглашение не пришло бы НИКОГДА: `triage`/`maintain` существуют только на репо ОРГАНИЗАЦИИ, а
`tonydzi` — `owner.type: User` (проверено API, не предположено: `422 Cannot assign permission of
triage`). Человек ждал 12 дней и за это время прислал ещё два смерженных PR. Ни один скан его не видел.

Поэтому на каждом прогоне — третий вопрос, дешёвый, по НАШИМ строкам за 30 дней:
```
gh api "/repos/tonydzi/<repo>/issues/comments?per_page=100" --paginate --jq \
  '.[]|select(.user.login=="tonydzi")|select(.created_at > "'"$(date -v-30d +%F)"'")|
   select(.body|test("(?i)\\binvite\\b|will send|\\bi.?ll\\b (send|open|give|add|file|ship)|waits for|arriving|coming shortly"))|
   "\(.issue_url|split("/")|last) @ \(.created_at): \(.body[0:120])"'
```
⚠️ Границы слов обязательны: без `\\b` шаблон `i.ll open` ловит «st**ill open**» — замер 27.09, одно
ложное попадание из трёх на первом же прогоне. Ложное срабатывание здесь дороже пропуска: оно гонит
рутину извиняться за долг, которого нет.

Каждое попадание = обещание с датой. Обещанного факта нет на сервере (нет инвайта, нет PR, нет релиза) →
это долг, и он СТАРШЕ входящих: молчание после «мы сделаем» дороже молчания после «спасибо».
⛔ Закрывать такой долг повторным обещанием запрещено. Закрывает либо сделанный факт, либо честный
разбор «обещание было невыполнимым, вот почему, вот реальные варианты» — второе законно и работает,
но только один раз на тред.
⚠️ И проверяй саму выполнимость ДО обещания: «прав нет / кнопка есть / доступ будет» — такой же CLAIM,
как причина (§5.4). Один вызов API вместо уверенности сэкономил бы здесь 12 дней чужого ожидания.

## Шаг 2-ноль — «наш он или нет» решается ДВУМЯ селекторами, а не одним
⛔ Прежде чем сказать «этот новый логин не наш, карточку не завожу» (так закрыли GALINA-KUKLEVA и dudididjdje-tech 13.09) — спроси GitHub ОБОИМИ вопросами:
```

gh api "search/issues?q=involves:<login>+user:tonydzi"  --jq '.total_count'   # он у нас АВТОР/упомянут
```
⚠️ ЗАМЕР 21.09.2026: по `commenter:` оба новых логина дали **0** — вывод «не наши» был готов и был бы ЛОЖНЫМ. `involves:` дал по **1**: FLiPPpro и b7n0de оказались АВТОРАМИ самоподач PR #4 и #5 в `tonydzi/awesome-verified-agents`. Автор PR, который не написал ни одного комментария, для `commenter:` невидим.
Правило: ноль по одному селектору = «этим селектором не видно», а не «человека нет» (§5.4, [[check-all-places-not-one]]). Хоронить контакт можно только когда молчат ОБА.

⚠️ ЗАМЕР 08.10.2026 (`hippoley`): у обоих селекторов есть ТРЕТИЙ ответ, которого правило выше не покрывало, — **422, а не ноль**. `commenter:`, `involves:` и `author:` все три вернули «The listed users cannot be searched either because the users do not exist or you do not have permission to view the users», при этом `/users/hippoley` отдавал живой профиль (`type=User`, не suspended), а `user:tonydzi` сам по себе отвечал `84`. То есть сломан не наш запрос и не аккаунт, а видимость логина в **search-индексе** (обычный случай — недавнее переименование; тот же класс, что «старый логин 422-ит в search API» в шапке рутины).
Разводи два исхода, они требуют разного:
- **0 у обоих** → «молчат оба», контакт можно хоронить;
- **422 у обоих** → прибор СЛЕП, вердикт о контакте запрещён вообще. Личность и касания проверяй обходом: `/users/<login>` + `/repos/tonydzi/<repo>/issues/<n>/comments` (issues API читает его нормально, поиск — нет).
⛔ 422 нельзя считать нулём: «не могу судить» и «его нет» — разные факты ([[instrument-must-not-be-blind]], §5.4). Диагноз делается ОДНИМ лишним вызовом — прогони селектор БЕЗ `user:tonydzi`: ответил 422 и там → виноват логин, а не наша половина запроса.

## Шаг 2 — ПРОВЕРИТЬ МОТИВ, прежде чем радоваться
⛔ Самая дорогая ошибка этого скилла — принять массового контрибьютора за фаната.
По каждому новому человеку обязательно:
```
curl -s -H "Authorization: Bearer $GITHUB_FLEET_FULL_PAT" \
  "https://api.github.com/users/<login>/events/public?per_page=100"
```
и посчитать: сколько PR за 90 дней, в сколько РАЗНЫХ репозиториев, повторяется ли один и тот же
патч у всех адресатов. Три класса, и вести себя с ними надо по-разному:

| Класс | Как выглядит | Что это значит | Наш ход |
|---|---|---|---|
| 🟢 глубокий | мало репо, много касаний в одном | человек реально пользуется | триаж-права, соавторство, звонок |
| 🟡 массовый качественный | 40+ PR в 20 репо, но патчи настоящие | конвейер репутации, идёт вглубь ТУДА, ГДЕ ОТВЕЧАЮТ | ответить в тот же день — скорость и есть весь рычаг |
| 🔴 массовый агентский | 40+ PR, текст сгенерирован, факты не сходятся | прогон чужого агента по случайным целям | честное «нет» с разбором + приглашение вернуться по существу |

Мотив пишем в карточку СЛОВАМИ и с уликой. «Пришёл сам» ≠ «мы ему нравимся»
([[prichina-kak-claim]]: причина — такой же claim, как вывод).

⭐ Первый вопрос про КАЖДОГО — **«мы туда стучались?»** (правило `external-signal-vs-reply-to-our-knock`,
замер 06.08). Три кучи, и они НЕ равны: (1) непрошеное — назвал нас в ЧУЖОМ треде, куда мы не
приходили → настоящий сигнал; (2) подали-приняли — мы отправили PR/заявку, редактор согласился →
считаем, но называем отдельно; (3) ⛔ ответ под НАШИМ собственным PR/issue → это отклик на наш стук,
за входящий интерес НЕ засчитывать. Наша исходящая работа физически рождает ответы, и они попадают
под тот же поиск, что органика — метрика внешней тяги ломается всегда вверх, в приятную сторону.

## Шаг 3 — проверить ЗАЯВЛЕННОЕ, а не поверить
Патч утверждает цифры (звёзды, лицензия, бенчмарк, «чинит X») — проверяю каждую своим прибором
до мержа. Мы лаборатория про проверяемость; смержить непроверенное утверждение о себе = сжечь
собственный тезис. Тесты гоняю ЛОКАЛЬНО на объединённой ветке, не доверяя зелёному CI:
```
git fetch origin 'refs/pull/*/head:refs/remotes/pr/*'
git checkout -B try<N> master && git merge pr/<N> && pytest -q
```

⭐ **Проверяю ТРИ вещи, а не одну** (боль 13.09 + 15.09, оба раза на sqlite-graph-memory):
1. **патч** — делает ли он то, что заявлено;
2. **тесты патча** — мутацией: откатываю починку и смотрю, КРАСНЕЮТ ли его тесты. 13.09 все 12
   остались зелёными на возвращённом баге: фикс был верный, тесты его НЕ держали. Мержу всё
   равно (двигать ворота после выполнения = обман), но свой красный тест дописываю сам;
3. ⭐ **не протух ли САМ ПАТЧ, пока лежал** — репозиторий едет под ним. 15.09: PR#7 чинил строку
   «no tests», а за пять дней ожидания PR#6 добавил 42 теста в соседний модуль, и написанная
   автором строка стала ложной ровно в момент мержа. Третье поколение одного дефекта в одном
   абзаце. Правило: патч, пролежавший дольше суток, перечитывается против ТЕКУЩЕГО состояния
   репозитория, а не против того, каким оно было при его отправке.

Если протух — это не повод не мержить и не повод винить автора. Мержим его работу под его
авторством, а дрейф чиним follow-up'ом сверху и НАЗЫВАЕМ его в треде: человек узнаёт то, чего
не мог знать, и это самая ценная часть ответа.

## Шаг 4 — ответить (голос Майкрофта, §3.3)
Первой строкой называюсь: «hi, this is Mycroft, Anton's synthetic co-founder». Один раз на тред.
Строчными, без ваты. Структура ответа, которая работает:
1. **Извиниться за задержку конкретно и назвать причину** — не «sorry for the delay», а что именно
   у нас не работало. Люди прощают поломку и не прощают отписку.
2. **Назвать, ЧТО ИМЕННО он поймал**, своими словами и по существу — доказательство, что читали код.
3. **Вердикт**: смержено / нужен ребейз с точной резолюцией конфликта / не берём и почему.
4. **Следующий шаг с датой** и один открытый вопрос.
5. ⭐ **Подпись-CTA последней строкой** (anton 10.09, голосовая hub:6539; supersedes прежнее
   «без подписи» в этом шаге). Одна строка со ссылкой `github.com/tonydzi`, формулировку
   варьировать. Источник текста — `$OBSIDIAN_VAULT/08-Templates/github-touch-signature.md`,
   карта поверхностей — `$OBSIDIAN_VAULT/08-Templates/outbound-signature.md`. Здесь это
   особенно дёшево и особенно окупается: человек УЖЕ пришёл к нам сам и уже читал наш код —
   это самый тёплый входящий, какой у нас бывает, а он уходил, не увидев, что рядом лежит
   ещё 60 репо. Carve-out против спама: одна подпись на тред — подписался, в следующих
   репликах того же треда можно без неё. Раскрытие Майкрофта = СВЕРХУ (первая строка),
   подпись = СНИЗУ; это разные блоки, один другого не заменяет.

Отказ пишу так же подробно, как согласие. Честное «нет» с разбором удерживает человека;
молчание не удерживает никого.

## Шаг 5 — завести в CRM в тот же заход
Каждый внешний человек:
- строка в `$OBSIDIAN_VAULT/_outreach/tracker.json` → `audience_A_engineers`
  (поля: handle `github:<login>`, channel `github`, warmth с УЛИКОЙ мотива, what_they_did,
  our_answer_at, ladder, next_step);
- карточка `$OBSIDIAN_VAULT/07-People/person-<slug>.md` с frontmatter
  `context: github-contributor`, `origin: github`, тегами `[person, github-contributor, engineer-funnel]`
  и обратными ссылками на артефакт (правило no-orphan).

## Шаг 5-бис — если в треде был СОВЕТ, а не только патч → в реестр кредита
Человек написал, ЧТО нам стоит сделать (даже одной строкой, даже без кода) — это вклад идеей,
и он обязан дожить до имени в CREDITS. Кладу строку сразу, не «потом»:
```
python ~/.claude/scripts/alpha_credit.py add --source gh \
  --author "<Имя или login>" --handle @<login> --url <ссылка на коммент> \
  --advice "<что посоветовал одной фразой>" --kind method|repo|tool|critique \
  --ref "gh:<owner/repo>#<номер>:<id коммента>"
```
`--ref` обязателен: этот скилл ходит по одному треду каждый день, без ключа один совет
размножится копиями. Дальше цепочка живёт в `/alpha-credit` (судить → испытать → спасибо → имя).

## Шаг 6 — контент
Входящий PR от постороннего = контентный момент по определению. Рефлекс [[content-miner-reflex]]:
```
python "$VAULT_IMPORTS/content-factory/content_miner.py" capture --title "<хук>" --note "<суть>" --tier medium
```
Сильная форма истории — не «нам прислали PR», а «что он поймал такого, чего не видели мы».

## Шаг 7 — вердикт

⚠️ **Красное у сторожа — это claim, а не приговор** ([[instrument-is-a-claim-too]]).
Перед ответом человеку сверь ДВЕ вещи, которых сторож не знает:
- **чей мяч по последнему касанию** — с 14.09.2026 он читает и РЕВЬЮ (`/pulls/N/reviews`),
  а не только комментарии треда; до этого канонический ответ по §4.7 был для него молчанием,
  и он печатал ВОЗРАСТ самого PR как долг (PR#7: 90.1 ч при PR, созданном 10.09 10:46Z);
- **срок, который мы САМИ дали автору** — этого сторож не знает вообще. Пообещали ждать
  правку до N-го числа — до N-го числа долга нет, и бампать нельзя, даже если строка красная.

✅ только когда: ноль просроченных долгов · мотив каждого нового человека проверен уликой ·
CRM пополнен · заявленные цифры перепроверены до мержа.
⚠️ если ответили, но не проверили мотив или не завели в CRM.
